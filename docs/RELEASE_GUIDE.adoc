 # Release Guide for RHDH 1.4+

This document seeks to explain the whole end-to-end process for releasing RHDH, from branch creation to GA push.

## Code Freeze / Blockers Only / New Stream Day

Run the branch creation script whenever dev is done (or nearly done) and it's time for feature (or code) freeze.

Once the branches are created, expect a flurry of last minute cherrypicks and requests for "can I include this non-blocker item too?" :this-is-fine: :this-is-the-way:

**Reject those requests** and send them to RM/PM/QE/Doc for approval as these should have already landed in the LOCKED test/doc plan weeks ago.

### Create branches (release-1.y, rhdh-1.y-rhel-9) + onboard new prod sec definition, Konflux application & components

Use the link:../build/scripts/tagRelease.sh[tagRelease.sh] script like this:
```
# to create release-1.7 + rhdh-1.7-rhel-9 branches, then update main + rhdh-1-rhel-9 branches
export GITHUB_TOKEN=<rhdh_bot_GH_token>
./build/scripts/tagRelease.sh -t 1.7 --branchfrom main -gh release-1.7
```

Script will create/update 1.y branches and update the main + rhdh-1-rhel-9 branches with minor version bumps for the GH and GL repos.

Prod sec and Konflux repos will also have MRs created for them to add a new RHDH 1.y version and associated applications/components.

## Release Candidates

Once the code freeze is achieved and all the last minute changes have stopped, you need to:

. disable the 1.y pipeline so you don't get any unexpected/unapproved changes in the release candidate
** Note that because a Konflux release uses *snapshots*, this is a step to avoid confusion; you should still be able to release an older snapshot if you forget this
** log in as rhdh-bot@redhat.com, then go to the link:https://gitlab.cee.redhat.com/rhidp/rhdh/-/pipeline_schedules[pipeline schedules] page
** find the correct pipeline, eg., for 1.6 
** uncheck the *Activated* box, and hit *Save changes*

. To rebuild the hub and operator images, you can use the triggerRespin.sh script; however, this will only work if there are changes applied to the midstream. If nothing has changed, then no Konflux build will be triggered. You should monitor Konflux and Quay to verify new builds are created correctly. See also link:RHDH-FAQ.adoc#user-content-how-to-respin[FAQ - How to respin].
+
```
./build/scripts/triggerRespin.sh 1.6 hub,op
```
+
. To create a new operator-bundle, use this
+
```
./build/ci/sync-midstream.sh --bundleonly --force -b rhdh-1.6-rhel-9 [--latest]
```
+
====
[NOTE]
The `--latest` flag is ONLY for the latest stable release, not for maintenance. For example if `main` branch is currently at version `1.6.0`, then the `release-1.5` branch (eg., `1.5.0`, `1.5.1`) is the "latest" branch. If releasing a `1.4.z` update, DO NOT use `--latest`. This alignment changes every quarter when a new release-1.y branch is created, aligning to a NEW set of `latest` tags.

## Summary of Release tasks:

### For a z-stream update, first do this

- collect the fixes in janus plugins + community plugins, and verify that they've been released to npmjs.com
- collect the updated plugin versions into showcase, and verify a downstream build has succeeded

### For all builds (y and z-stream)

- Use link:../build/scripts/kfuxRelease.sh[kfuxRelease.sh] to push the latest snapshot to stage 
- coordinate with QE and Doc via slack and email notifications of RC builds and progress of testing, doc readiness, etc.
- remind QE to announce test completion; watch while the builds are pushed (1-2 hrs?); complain on slack in various rel-eng channels if things break while pushing

### Once the containers have shipped 

- re-render FBCs to refer to registry.redhat.io instead of quay.io
- generate the helm chart PR for the openshift helm charts repo; monitor until it's merged
- release the FBCs to production
- smoke test the operator and helm installs
- notify Docs that they can release the latest RN updates
- tag the repos w/ new 1.y.z tag; bump the repos 1.y.(z+1) to prepare for subsequent releases
- for a .0 release, remove EOL versions of RHD from Comet
