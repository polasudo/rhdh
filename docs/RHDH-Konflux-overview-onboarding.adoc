1. Ask that person to go to https://konflux.apps.stone-prod-p02.hjvn.p1.openshiftapps.com/application-pipeline/workspaces/rhdh/applications

## Onboarding a new y-stream release

Once a quarter, new branch are created in GitHub called `release-1.y` for the new release. 
In the link:https://gitlab.cee.redhat.com/rhidp/rhdh[rhidp/rhdh Gitlab repo], an equivalent branch called `rhdh-1.y-rhel-9` is created.
Once these exist, a new Application, with 3 (or more) components can then be added.

This should be configured so that for any new build of the rhdh-hub or rhdh-operator containers, a new rhdh-operator-bundle is theen built; once that is built, the bundle should nudge the FBC applications to update those with fresher digests.

## File Based Catalogs (FBCs)

FBCs replace IIBs (index bundles) in RHDH 1.4+.

### Add a new Application and Component to build FBCs for a new OCP version

This should only be done once every 6mo or so, when a new OCP version is released and a new version of registry.redhat.io/openshift4/ose-operator-registry-rhel9 becomes available.

1. Go to https://konflux.apps.stone-prod-p02.hjvn.p1.openshiftapps.com/application-pipeline/workspaces/rhdh/applications

2. Update defaults in link:https://gitlab.cee.redhat.com/rhidp/rhdh/-/blob/rhdh-1-rhel-9/build/scripts/renderCatalogs.sh[build/scripts/renderCatalogs.sh]

3. Create a new Application and Component. Note that an MR will be generated to add new pipelines to https://gitlab.cee.redhat.com/rhidp/rhdh/-/tree/rhdh-1-rhel-9/.tekton -- you can probably merge those as is, then update them to match the customizations applied to the other fbc-related pipelines. 

image::images/new-application-fbc-component.png[New Application and Component]

### Remove support for EOL OCP versions

When support for an older version of OCP is to be dropped, FBC publishing for that old version can be stopped.

1. Delete the fbc application

2. Update lifecycle docs & official product docs, release notes, etc. 

3. Update defaults in link:https://gitlab.cee.redhat.com/rhidp/rhdh/-/blob/rhdh-1-rhel-9/build/scripts/renderCatalogs.sh[build/scripts/renderCatalogs.sh]

### Performing a release

Sadly, we have two options for releases in Konflux:
* everything immediately released as long as the tests pass, or
* link:https://konflux.pages.redhat.com/docs/users/releasing/releasing-products.html#_authoring_releases[manual releases via yaml chunks] or using the clunky UI

1. find the set of snapshots you want to release. For 1.4 this is 3 containers and 5 FBCs.

2. Log into the cluster at https://console-openshift-console.apps.stone-prod-p02.hjvn.p1.openshiftapps.com/k8s/ns/rhtap-releng-tenant/core~v1~Pod using the link under your name to Copy login command. 

3. Run that command in a console, eg., 
+
```
oc login --token=sha256~YOUR_TOKEN_HERE --server=https://api.stone-prod-p02.hjvn.p1.openshiftapps.com:6443
```
+
4. Next, sequentially, appy Release yamls like this:

```
echo "apiVersion: appstudio.redhat.com/v1alpha1
kind: Release
metadata:
  name: manual-release-rhdh-1-4-fbc-4-14-stage-2
  namespace: rhdh-tenant
  labels:
    release.appstudio.openshift.io/author: 'nboldt'
spec:
  releasePlan: rhdh-1-4-fbc-4-14-stage-release-plan
  snapshot: fbc-4-14-d766t
" |  oc apply -f -
```

Note also this mapping: 

* If image is pushed to: quay.io/redhat-pending/rhdh----rhdh-operator-bundle:1.4
* refernce it as this:   registry.stage.redhat.io/rhdh/rhdh-operator-bundle:1.4

To check that your stage push is the latest / correct version:

```
for d in /rhdh/rhdh-hub-rhel9:1.4 /rhdh/rhdh-rhel9-operator:1.4 /rhdh/rhdh-operator-bundle:1.4; do \
  for r in registry.stage.redhat.io quay.io; do
    echo; echo ${r}${d}; \
    skopeo inspect docker://${r}${d} > /tmp/inspect.txt && \
    jq -r '.Labels.version+"-"+.Labels.release+" built on "+.Labels."build-date"' /tmp/inspect.txt && \
    jq -r '.Env[]|select(.|contains("_REPO"))' /tmp/inspect.txt && \
    jq -r '.Labels."vcs-ref"' /tmp/inspect.txt && \
    rm -f /tmp/inspect.txt
  done
  echo "-----"
done
```
